## 1. Python 执行与 Slate 提交

**5.8.2 已验证的替代通道**：Epic 随引擎提供的 `PythonScriptPlugin/Content/Python/remote_execution.py`。通过 UE MCP 的 ObjectTools 设置 PythonScriptPluginSettings 的 `bRemoteExecution=true`，组播绑定 `127.0.0.1`、TTL=0；外部 Python 发现与本项目路径一致的编辑器后 `open_command_connection()` / `run_command()`。无需焦点、键入或额外文件监听插件。

已提供 `Scripts/ue_python.py`：每次调用先通过 MCP 在当前编辑器启用本机通道，再执行指定脚本；编辑器重启后可直接重新调用。多次资产修改、FBX 导入和 PIE Tick 验收均已实测。

```powershell
python Scripts/ue_python.py Scripts/M1_diag.py
python Scripts/ue_python.py Scripts/M1_finalize_assets.py
python Scripts/run_m1_acceptance.py
```

**1a 的根因不能仅由原记录确认。** 本机 5.8 插件源码 `SlateInspectorToolset.cpp::PressKey` 当前接受 Key 字符串（不是 Widget ref），向现有焦点发送 KeyDown、Enter 对应 `\r` 的 KeyChar、KeyUp，最后无条件返回 true；返回 true 不能证明命令提交。首先确认焦点所在的内部 EditableText 和编辑器 Modal/PIE 状态。本次没有继续复现 OS/Slate 焦点竞争，也没有修改引擎插件。

一般经验：只模拟 KeyDown 并不等价于完整的 OS 文本输入事件序列；但本机实现已经补发 Enter 字符事件，不能把缺少 KeyChar 宣称为本次已证实原因。

**1c**：`-run=pythonscript` 可作为离线资产流水线的备选，必须显式加载所需地图/资产，并检查返回值和保存结果。Commandlet 不能替代交互式 PIE/Slate/视口验证。本次实际采用在线 Remote Execution，未执行 commandlet，不把它标为“5.8 已验证”。

## 2. 蓝图 CDO、编译与保存

“save_asset 必然用旧 CDO 覆盖内存”的推断没有获得本次证据支持。本机 `EditorAssetSubsystem.cpp` 中 `SaveAsset` 先解析路径，再调用 `SavePackages`；`SaveLoadedAsset` 也走 `SavePackages`。这不足以证明此前失效的具体原因。

**5.8.2 已验证流程**（见 `M1_finalize_assets.py`）：PIE 停止 → 加载蓝图并编译 → 获取 generated_class 的 CDO → `set_editor_property()` 修改正确的 CDO/组件模板 → 编译 → `save_loaded_asset(bp, only_if_is_dirty=False)` → 重新获取 generated_class/CDO 断言 → PIE 检查实例。之后完整重开编辑器并重新 PIE，值仍正确。

另做了有实际数值变化的同会话试验：将 SpawnSafetyMargin 从 4 改为 7，编译/保存后直接 PIE，GameMode 实例读到 7；停止 PIE 后恢复为 4 并保存，未重启编辑器。[原始证据](../开发过程/验收记录/M1_CDO_Roundtrip.json)，复现入口 `python Scripts/run_m1_cdo_check.py`。

- 编译可能重建 GeneratedClass/CDO，不跨编译持有旧引用继续读取。
- `FighterClass` 属于角色 GameMode 生成类的默认属性，不是 UBlueprint 容器的同名字段。
- 包路径与对象路径都可解析到资产；保存失败有 false/日志，应检查返回值。本次使用加载后的资产引用消除字符串路径歧义；没有证据认定带对象名的路径必然静默失败。
- `set_editor_property` 进入编辑器属性通知链；必要的资产结构编辑可 `modify()`。保存对象应是 Blueprint/资产，不是把 CDO 当作独立资产保存。

另外找到一个已证实的“写成功却不生效”问题：**UE 5.8 InputMappingContext 使用 `default_key_mappings.mappings`**。原脚本写的是弃用 `mappings`；已修复并通过真实 Enhanced Input Action 分发验证。

## 3. 编辑器重启后的 MCP 会话

Codex 已配置 `unreal-mcp`，地址 `http://127.0.0.1:8000/mcp`；通过 `codex mcp add unreal-mcp --url ...` 添加，符合 [官方 MCP 配置文档](https://developers.openai.com/codex/mcp/)。当前任务使用 `Scripts/ue_mcp.py` 直连，不依赖本轮工具目录热更新。

**已验证**：客户端每次命令调用都新建 `initialize` → `notifications/initialized` → `tools/call` 会话，不复用上一编辑器进程的 Session ID；编辑器多次重启后恢复正常。工具发现先 `list_toolsets`，再 `describe_toolset`，最后 `call_tool`。

ZCode 的自动重连配置/实现本次未核验，不能承诺某个信号或配置能修好它。旧客户端遇 Unknown session id 时应重新握手；若客户端不支持，重开连接/客户端或使用上述独立调用工具。超时不代表写操作没执行，不能盲目重放 Spawn/导入；先核验状态。

## 4. 出生挤开与角色重生

**5.8.2 已验证**：本关卡两个 PlayerStart 的 root 改为 `set_collision_profile_name('NoCollision')` 并保存后，P1/P2 每次出生 XY 回到 `(-500,0)` / `(500,0)`，不再 Y=-67。标记仅用于编辑器参考，实际坐标仍统一来自 GameMode。

项目已覆写 RestartPlayer，所以保留单一 GameMode 生成入口即可；使用标准 FindPlayerStart 是另一种组织方式，并非当前必须重构的条件。`DefaultPawnClass=None` 明确避免默认 Pawn 与手工生成并存。

补充实测发现：Destroy 后马上用同一个固定 Actor Name 重生会触发引擎 Fatal（旧 UObject 未回收）。已改 `FActorSpawnParameters::NameMode=Requested`，允许 `Fighter_P2_1` 等后缀；身份使用 FighterRole/槽位，连续重生测试通过。

## 5. 双通道方案评估

离线 commandlet 做资产批处理、在线编辑器做 PIE 是合理备选，但本项目无需为每次资产调整关闭编辑器。优先采用本次已验证的 **MCP 会话管理 + 本机 Remote Execution**：同一个编辑器世界可直接完成编译、保存、导入与运行检查。

保留以下边界：修改 C++ 反射/构造布局时保存关闭编辑器、构建、重开；资产修改必须停止 PIE；异步 Tick 测试不阻塞游戏线程，并有超时、清理及文件结果；不要让两个进程同时写同一份 Content/Config。共享 DDC 本身不等同于资产写入安全。

截图也需区分：本机 `CaptureViewport` 实测抓取的是编辑器场景视口，PIE 时也可能看不到运行角色。实际游戏画面使用 `CaptureEditorImage` 或游戏 HighResShot，捕获后人工查看结果，不能仅按 API 返回成功判定。

原卡点已通过上述工作流绕开；未声称修复 ZCode 客户端本身或 Slate 事件路由。本项目 M1 的实际功能与重进验收已经通过。
