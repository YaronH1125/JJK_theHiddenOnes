版本：v0.1；建立日期：2026-09-15；实施与自测状态：待核验。

[开发过程导航](README.md) · 上一阶段：[M6](M6_角色与技能表现.md) · [总计划](../05_开发计划与验收.md)

## 1. 目标与进入条件

当前交付范围按 [08](../08_石流龙战斗系统设计.md) 增加近远程形态、拳腿轻重击、咒力与原创领域。领域的视觉推断/原创名称在技术说明中明示，不宣称官方复刻。

将 M6 的完整角色闭环整理为别人可以独立运行、观看和理解的求职作品。M0—M6 的阻塞问题应已关闭，有实际验收记录和正式角色独立包。

交付包括运行包、操作说明、演示视频、技术说明、性能记录和已知问题。最终结论以同一个交付版本为准，不用不同版本的局部成功拼成完整验收。

## 2. 交付物清单

| 交付物 | 必须包含 |
| --- | --- |
| Windows 独立运行包 | 可执行程序及全部必要目录、版本标识、启动方式 |
| 操作说明 | 实际按键、训练模式/开关、技能、重置、退出、目标环境 |
| 演示视频 | 正式角色、攻防、炮击、训练、AI 与重开；注明版本 |

| 性能记录 | 硬件、分辨率、画质、构建、场景、采样时长和帧时间依据 |
| 验收与限制 | 用例结果、缺陷/修复记录、占位内容、未验证环境 |

先在本地整理交付目录与压缩包；公开上传、发布平台或发送给别人属于后续具体任务，不作为本阶段文档默认执行动作。

## 3. 开发步骤与局部检查

### M7.1 固定交付候选版本

记录提交号或可恢复快照、引擎与配置。整理 M0—M6 的问题，区分阻塞运行/主闭环问题与不影响体验的限制；未执行用例不能直接标通过。

清理确实未引用的模板资源和开发测试能力，使用编辑器检查依赖与引用，不按目录名直接删除。整理后的工程重新构建并做相关回归。

局部检查：交付候选包含哪些功能和资产可追溯，没有为了隐藏错误而关闭关键规则。

### M7.2 构建与打包

明确最终构建配置、默认启动地图、打包平台、所需运行库及资源 Cook 范围。先保留 Development 包用于定位问题，再按实际展示需要选择最终包配置；更换配置后必须对最终包重测。

打包到独立输出目录，记录完整日志。检查运行入口不依赖编辑器、旧工程路径、临时测试地图或用户 Saved 中的私有配置。资源通过真实引用或明确配置纳入包。

局部检查：编辑器关闭时能运行包，正式石流龙、全部技能、UI 与 AI 均正常。

### M7.3 用干净运行环境验证

优先复制压缩包到另一台目标平台机器，或新用户/干净目录环境解压启动。不要删除开发者原 Saved 来冒充干净测试；使用隔离的运行环境。

先不看源代码，按操作说明执行所有主要流程，验证必要运行库提示和可执行入口。只复制最终交付物，不额外从工程补文件。

局部检查：目标环境可以从交付物独立复现主流程；如只能本机测试，明确写出验证边界，不能宣称新机器通过。

### M7.4 写操作说明与录演示

按当前 Input Action 绑定核实键位，说明锁定与回正区别、两技能和绝技使用条件、训练开关和重置语义。记录窗口模式/分辨率和退出入口。

建议视频依次展示：进入场景与自由镜头 → 普攻/防御/投技/取消 → 重拳和炮击 → 训练开关与统计 → AI 对局 → 死亡重开。长度按内容决定，不通过剪辑隐藏必须手工修状态的问题。

局部检查：新读者能仅按说明完成操作；视频与交付包功能和键位一致，占位/计划内容明确标注。

### M7.5 整理技术说明与实现证据

用一个真实攻击案例讲清请求、GA、Montage、窗口、检测、结算、GE、受击与 HUD。引用最终代码中的实际类名和文件位置，不沿用未落地的建议名。

说明三个核心问题：如何避免同段重复命中；如何在取消/死亡/重置清理状态；AI 如何共用玩家规则。补充炮口遮挡、自由镜头与目标解耦、资源/训练口径，并解释原型取舍。

局部检查：每个技术结论能指向实现或验收证据；不宣称已有联网预测、回滚或确定性模拟。

### M7.6 做有上下文的性能测量

记录 CPU/GPU/内存、分辨率、画质、垂直同步/帧率限制、构建配置和测量工具。场景至少包括静止训练、AI 持续攻防、炮击/蓄力特效和连续重置后的战斗。

每个场景先预热，再用固定时长（建议至少 60 秒）采样；记录实际帧时间分布、明显峰值及对应 CPU/GPU 工作。采用 Unreal Insights 等工具定位主要瓶颈，优化后只针对相关场景复测并保留前后数据。

本项目尚未承诺统一帧率预算。先根据目标设备记录预算，再评估是否达标；不使用空场景平均 FPS 代替完整战斗性能。

局部检查：性能结论可根据场景与原始记录复现，长帧原因和未解决限制写清楚。

### M7.7 归档与最终一致性检查

将运行包、说明、录像、技术文档和性能报告关联到同一版本，给压缩包记录文件大小与校验值。重新解压后走最终闭环，确认资源未遗漏。

同步 [总计划](../05_开发计划与验收.md) 的完成状态，保留已知限制和后续改进项；不能将“已录视频”替代运行包验收。

## 5. 最终闭环脚本

解压交付包 → 按说明启动 → 默认木桩练三段普攻 → 固定防御练投技与取消 → 使用基础/强化炮击 → 查看训练统计并重置 → 开 AI 完成对局 → 重开 → 退出并重新启动。

这个流程必须由交付包独立完成。记录执行人、环境、版本、结果和证据位置；如果在新机器无法完成，修复或明确缩小已验证范围后重新验收。

## 6. 最终完成标准

- [ ] 最终运行包主流程和关键异常用例通过，无未解决的崩溃/永久卡死/缺资源问题。
- [ ] 操作说明、演示视频、技术说明与实际版本一致。
- [ ] 性能报告有真实测量，目标环境与未验证项明确。
- [ ] 所有交付物可定位、可解压、可运行，具备版本和完整性记录。
- [ ] 总计划更新实际状态，未来工作与本次完成内容清楚区分。

只有文档、源码或视频，没有独立运行包时，M7 不算闭环。交付完成后的优化另开具体事项，不无限扩展当前首版。
