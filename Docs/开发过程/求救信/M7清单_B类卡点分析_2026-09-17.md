## 3. 为什么一直卡在这里（卡点分析）

**直接现象**：B 类套件每次跑到 13 项（B02 持炮 10s/60s、超级炮 10s/60s、冷却全部通过之后，进入 B03 的输入注入代码）时，UE 编辑器主线程彻底冻结——日志完全停止、报告停在 13、MCP 端口不再应答（HTTP 超时），只能强杀进程重启。本轮复现两次，检查点一致。

**头号嫌疑：`subsystem.inject_input_vector_for_action(...)` 从 Slate post-tick 的 Python 回调里调用。**
- 这是 B03 新引入的调用（为了"真实输入路径"验证右键瞄准与左键蓄力），此前所有套件从未在 PIE 内逐帧注入过输入。
- 冻结无任何异常日志——典型的主线程死锁/阻塞等待，而非 Python 异常（Python 异常会被 tick 捕获并写入报告 failed，状态不会停在 running）。
- 时序吻合：两次都停在 B02 结束、B03 第一条注入语句即将执行的边界。

**次要因素（已修复或已规避，但拖慢了排查）**：
1. 编辑器窗口失焦后 CPU 节流到 ~3fps（M5 套件有 `bThrottleCPUWhenNotForeground=False`，B 套件初版遗漏）→ 大量"until 超时/伤害窗口串扰"的假失败，第一轮 13 失败大部分由它造成。
2. MCP HTTP 在编辑器主线程繁忙/冻结时 60s 超时（HTTP 000），runner 因此中断但 PIE 内的套件继续跑——导致"runner 报超时、报告却在推进"的错觉。
3. 远程执行通道每次编辑器重启后需要重新握手，偶发 connect refused，重试即可。

**为什么不是这些**：
- 不是 B02 逻辑本身：13 项里 B02 的 6 项全部 PASS（10s/60s 持炮不发射不回咒、满蓄伤害 90/220、冷却拒绝）。
- 不是报告写入序列化问题：M6 时代那类崩溃已用 `list()` + 容错 finish 修掉。
- 不是资源/数值：B01 全链路（近战积能→领域自然开启→球破防→到期→收尾击杀→胜负→重置）除 orb_vs_guard 一项外全部 PASS。
